# AnomalyFlow
## A Hybrid Deep Learning and Statistical Framework for Stealthy Low-Rate DDoS Detection

---

# Purpose

This document records the key technical decisions made during the development of the project along with the rationale behind each choice. These decisions guide implementation, ensure consistency across notebooks, and provide justification for the methodology used in the final report.

---

# Dataset Selection

### Decision
Use the CIC-DDoS2019 dataset.

### Reason
- Publicly available benchmark dataset.
- Contains multiple DDoS attack types.
- Includes benign traffic for realistic classification.
- Widely used in cybersecurity research, enabling fair comparison with existing work.

---

# Data Preprocessing

### Decision
Merge all processed CSV files into a single dataset.

### Reason
Training a single model on all attack categories allows the model to learn generalized traffic behavior rather than specializing in one attack type.

---

### Decision
Remove identifier columns.

### Removed Columns
- Flow ID
- Source IP
- Destination IP
- Timestamp

### Reason
These fields uniquely identify flows but do not describe traffic behavior. Retaining them could introduce bias and reduce the model's ability to generalize.

---

### Decision
Remove constant columns.

### Reason
Features with no variation provide no useful information and unnecessarily increase computational cost.

---

### Decision
Handle missing and infinite values during preprocessing.

### Reason
Deep learning models require clean numerical input. Missing or infinite values can cause training instability or runtime errors.

---

# Train-Test Split

### Decision
Do not split the dataset during Model Preparation.

### Reason
Sliding-window feature engineering must be performed before splitting so that temporal windows remain intact. Splitting first could break window continuity and introduce inconsistencies.

---

# Feature Engineering

### Decision
Use sliding windows.

### Window Size
100 flows

### Reason
A window of 100 flows provides sufficient temporal context to capture evolving traffic behavior while remaining computationally manageable.

---

### Decision
Use overlapping windows.

### Stride
20 flows

### Reason
Overlapping windows improve temporal continuity and increase the likelihood of capturing gradual transitions between benign and attack traffic.

---

### Decision
Assign the majority label to each window.

### Reason
Most flows within a window typically belong to the same traffic class. Majority voting provides a simple, robust, and reproducible labeling strategy.

---

# Statistical Features

### Decision
Extract statistical descriptors instead of using raw flow values directly.

### Selected Features
- Flow Duration
- Flow Bytes/s
- Flow Packets/s
- Packet Length Mean
- Packet Length Std
- Total Forward Packets
- Total Backward Packets
- Average Packet Size

### Reason
These features summarize important characteristics of network traffic, including packet volume, timing, packet size, and communication patterns. They provide compact representations suitable for deep learning while reducing redundancy.

---

### Decision
Compute the following statistics for each selected feature.

- Mean
- Standard Deviation
- Variance
- Minimum
- Maximum
- Rényi Entropy

### Reason
These statistical measures capture both central tendency and variability within each traffic window, enabling the model to distinguish between normal and malicious traffic patterns.

---

# Rényi Entropy

### Decision
Use Rényi Entropy instead of relying solely on conventional statistical measures.

### Alpha
2

### Reason
Rényi entropy emphasizes repeated traffic patterns and provides greater sensitivity to concentration within probability distributions. This makes it well suited for identifying structured traffic generated by stealthy low-rate DDoS attacks.

---

# Chunk-Based Processing

### Decision
Process the dataset in chunks.

### Chunk Size
50,000 rows

### Reason
The merged dataset contains approximately 67.8 million flow records, which cannot be processed efficiently in memory on a 16 GB system. Chunk processing ensures constant memory usage while maintaining scalability.

---

### Decision
Write engineered features directly to disk.

### Reason
Avoid storing millions of engineered samples in RAM. Incremental writing reduces memory consumption and enables recovery if processing is interrupted.

---

# Engineered Dataset

### Decision
Generate one engineered feature vector per sliding window.

### Output Features
- Statistical descriptors
- Rényi entropy values
- Window label

### Reason
The engineered dataset becomes the standardized input for the deep learning model and significantly reduces data dimensionality while preserving meaningful traffic information.

---

# Deep Learning Architecture

### Decision
Use a hybrid CNN–BiLSTM–Attention architecture.

### Reason

CNN
- Learns local feature interactions.
- Detects spatial relationships among engineered traffic features.

Bi-LSTM
- Learns temporal dependencies between sequential traffic windows.
- Captures both past and future context.

Attention
- Focuses the model on the most informative temporal patterns.
- Improves interpretability and classification performance.

---

# Severity Prediction

### Decision
Include an attack severity prediction stage.

### Reason
Most existing research focuses only on attack detection. Predicting attack severity enables prioritization of mitigation strategies and improves the practical usefulness of the framework.

---

# Mitigation Engine

### Decision
Integrate a mitigation engine after classification.

### Planned Actions
- IP blocking
- Rate limiting
- Alert generation
- Priority assignment

### Reason
Detection alone is insufficient for real-world deployment. Automated mitigation transforms the framework from a passive detector into an actionable security system.

---

# Dashboard

### Decision
Develop a visualization dashboard.

### Reason
A dashboard enables security analysts to monitor traffic, view predictions, analyze attack severity, and observe mitigation actions in real time.

---

# Handling Class Imbalance

### Decision
Use class-weighted loss during model training.

### Reason
The engineered dataset contains millions of samples with significant class imbalance. Class-weighted loss preserves the original data distribution while reducing bias toward majority classes.

---

### Decision
Do not use SMOTE or synthetic oversampling initially.

### Reason
Synthetic samples may distort temporal characteristics of network traffic and substantially increase computational cost on an already large dataset.

---

# Model Evaluation

### Planned Metrics
- Accuracy
- Precision
- Recall
- F1-score
- ROC-AUC
- Confusion Matrix

### Reason
These metrics provide a comprehensive evaluation of classification performance, especially under class imbalance.

---

# Model Saving

### Decision
Save the best-performing model based on validation performance.

### Reason
Prevents overfitting and ensures that the deployed model generalizes well to unseen data.

---

# Design Principles

The project follows the following engineering principles:

- Modular notebook design.
- Independent execution of each notebook.
- Chunk-based processing for scalability.
- Production-quality implementation.
- Clear documentation and reproducibility.
- Avoid hidden notebook dependencies.
- Memory-efficient processing.
- Real-world deployment focus instead of paper reproduction.

Develop a scalable, explainable, and deployable hybrid DDoS detection framework that combines statistical traffic analysis with deep learning to improve the detection of stealthy low-rate DDoS attacks while providing intelligent mitigation and real-time visualization.

# Decisions Made During Notebook 06 Development

Notebook 06 implements the project-specific AnomalyFlow decision and security layer around the frozen CNN-BiLSTM-Attention baseline.

### Decision
Keep the trained CNN-BiLSTM-Attention model frozen during AnomalyFlow development.

### Reason
The purpose of Notebook 06 is to add a decision/security layer around the established baseline rather than retraining or arbitrarily modifying the baseline architecture.

---

### Decision
Use model prediction confidence as a model-uncertainty signal.

### Reason
Lower prediction confidence was strongly associated with baseline prediction errors. This provides a model-side uncertainty signal that can complement statistical traffic evidence.

---

### Decision
Use the eight existing Rényi entropy features generated by Notebook 04 as the statistical evidence source.

### Rényi Features
- Flow Duration_Renyi
- Flow Bytes/s_Renyi
- Flow Packets/s_Renyi
- Packet Length Mean_Renyi
- Packet Length Std_Renyi
- Total Fwd Packets_Renyi
- Total Backward Packets_Renyi
- Average Packet Size_Renyi

### Reason
These features already exist in the engineered dataset and provide a consistent statistical representation without requiring another feature-engineering pipeline.

---

### Decision
Combine confidence uncertainty and Rényi statistical evidence into the AnomalyFlow score.

### Configuration
- Confidence weight: 0.5
- Rényi weight: 0.5

### Reason
Equal weighting provides a neutral combination of model uncertainty and statistical evidence.

---

### Decision
Use the validation set to establish AnomalyFlow thresholds.

### Reason
Thresholds must be determined before final test evaluation and must not be tuned using the test set.

---

### Decision
Freeze the following AnomalyFlow decision thresholds.

Score < 0.25
→ NORMAL

0.25 ≤ Score < 0.40
→ SUSPICIOUS

Score ≥ 0.40
→ HIGH_EVIDENCE

### Reason
Validation results showed a strong increase in baseline prediction error rate across the three states.

Validation error rates:

- NORMAL: 3.05%
- SUSPICIOUS: 32.71%
- HIGH_EVIDENCE: 49.44%

---

### Decision
Apply the frozen validation configuration to the untouched test set without further threshold tuning.

### Reason
This provides an unbiased evaluation of whether the AnomalyFlow decision layer generalizes to unseen data.

---

### Decision
Treat AnomalyFlow states as evidence/uncertainty states rather than directly equating them with DDoS severity.

### Reason
AnomalyFlow measures combined model uncertainty and statistical evidence. It is not itself a direct DDoS probability.

---

### Decision
Perform a separate binary DDoS interpretation from the 17-class predictions.

### DDoS Classes

- DrDoS_DNS
- DrDoS_LDAP
- DrDoS_MSSQL
- DrDoS_NTP
- DrDoS_NetBIOS
- DrDoS_SNMP
- DrDoS_SSDP
- DrDoS_UDP
- MSSQL
- NetBIOS
- Portmap
- Syn
- TFTP
- UDP
- UDP-lag

### Non-DDoS Classes

- BENIGN
- LDAP

### Reason
Multiclass attack classification and binary DDoS detection measure different objectives and should be reported separately.

---

### Decision
Generate security severity using predicted DDoS status together with the AnomalyFlow state.

### Severity Mapping

Predicted Non-DDoS + NORMAL
→ NORMAL

Predicted Non-DDoS + SUSPICIOUS
→ MONITOR

Predicted Non-DDoS + HIGH_EVIDENCE
→ INVESTIGATE

Predicted DDoS + NORMAL
→ LOW

Predicted DDoS + SUSPICIOUS
→ MEDIUM

Predicted DDoS + HIGH_EVIDENCE
→ HIGH

### Reason
This preserves the classifier's attack classification while using AnomalyFlow evidence to prioritize security attention.

# Decisions Made During Notebook 07 Development

### Decision
Use a severity-based mitigation engine that converts Notebook 06 security severity into explicit mitigation actions.

### Mitigation Mapping

NORMAL
→ NO_ACTION

MONITOR
→ MONITOR

INVESTIGATE
→ INVESTIGATE

LOW
→ ALERT_AND_LOG

MEDIUM
→ RATE_LIMIT

HIGH
→ BLOCK_AND_RATE_LIMIT

### Reason
The mitigation layer converts detection and security-severity decisions into actionable responses while maintaining graduated mitigation based on the strength of the available evidence.

---

### Decision
Keep Notebook 07 mitigation actions simulation-based while separating mitigation decision logic from actual network enforcement.

### Reason
Notebook 07 operates on the verified Notebook 06 sample-level artifact and does not contain source-IP/network-control information required for live enforcement. The mitigation engine therefore records the actions that should be taken without directly modifying network infrastructure.

---

### Decision
Reserve actual blocking and rate-limiting enforcement for the backend/deployment layer.

### Reason
The final deployed system should be capable of receiving mitigation decisions for new traffic and enforcing actions through an appropriate network-control mechanism. This keeps the detection and decision pipeline independent from firewall or network-device implementation.

---

### Decision
Treat Notebook 07 simulated blocking as a mitigation decision, not as evidence of actual network blocking.

### Reason
This maintains a clear distinction between evaluated mitigation decisions and real-world enforcement. Notebook 07 demonstrates that 30,736 test samples would receive a BLOCK_AND_RATE_LIMIT decision, while actual enforcement remains a deployment-stage capability.

---

### Decision
Design the mitigation engine to support new incoming traffic after deployment.

### Reason
The Notebook 07 test-set evaluation validates the mitigation logic using previously evaluated samples, while the final system is intended to apply the same detection, severity, alert, and mitigation decision pipeline to new traffic.
